## 專案概述

本專案為早餐店前後端管理系統，以 V9 為基礎導入 V10 RBAC（Role-Based Access Control）權限管理。系統支援五種角色，每種角色各有對應的操作範圍，確保資料安全與職責分離。

角色資料以 PostgreSQL array 欄位存於 `user` 表，權限邏輯集中於 `shared/guards.ts`，遵循 V10 三層事實架構設計。

---

## 角色定義

依照 V10_RBAC 規格，系統定義以下五種角色：

| 角色（英文） | 中文稱呼 | 說明 |
|---|---|---|
| **customer** | 顧客 | 一般消費者，可自行點餐 |
| **staff** | 店員 | 負責現場服務與叫號取餐 |
| **chef** | 廚師 | 負責備餐，需看到待處理訂單 |
| **owner** | 店長 | 管理菜單與查看營運數據 |
| **admin** | 系統管理員 | 完整系統控制，管理帳號與角色 |

> 新註冊使用者預設為 `customer`。升級至 `staff`／`chef` 需申請，`owner`／`admin` 只能由現有 admin 直接指派。

## 功能規劃（完整願景）

### 顧客（customer）

**基本功能**
- 瀏覽當前菜單（含分類篩選）
- 建立購物車訂單、修改數量
- 提交訂單並查看自己的訂單歷史

**進階規劃**
- 對已完成訂單給予 1–5 星評分，並可附留言
- 查看訂單目前的備餐狀態（待備餐 / 備餐中 / 可取餐）
- 收藏常點品項，下次快速重點
- 訂單完成後推播通知（取餐提醒）

---

### 店員（staff）

**基本功能**
- 查看所有已提交的訂單
- 協助顧客完成點餐操作（代客點餐）

**進階規劃**
- 叫號管理：依時間順序將訂單標記為「已叫號」
- 查看當前等候隊列，掌握現場狀況
- 標記訂單為「已取餐」，完結整個流程

---

### 廚師（chef）

**基本功能**
- 查看所有狀態為「已提交」的待處理訂單
- 依下單時間排序，確保先進先出

**進階規劃**
- 將完成備餐的訂單標記為「可取餐」（通知店員叫號）
- 查看各品項的今日備餐數量（備料參考）
- 顯示備餐時間統計（平均完成速度自我監控）

---

### 店長（owner）

**基本功能**
- 新增、修改、刪除菜單項目
- 查看所有訂單（含顧客資訊）

**進階規劃**
- 每日營業報表：總訂單數、總營業額、各品項銷售排行 Top 5
- 查看週/月趨勢圖（銷售走勢）
- 設定品項的促銷價格與有效期間
- 匯出訂單報表為 CSV

---

### 系統管理員（admin）

**基本功能**
- 擁有所有角色的完整操作權限
- 直接指派任意使用者的角色
- 審核角色升級申請（staff／chef）

**進階規劃**
- 查看所有已註冊使用者列表
- 停用帳號（軟刪除，保留訂單歷史）
- 查看系統操作紀錄

## MVP 範圍

考量開發時間，本次實作以下最小可行範圍：

### 各角色核心功能（各一項新功能）

| 角色 | MVP 新功能 | 說明 |
|------|-----------|------|
| customer | **訂單評分** | 對已提交訂單評 1–5 星 |
| staff | **叫號** | 將訂單標記為已叫號（`ready` → `called`） |
| chef | **標記出餐** | 將訂單標記為可取餐（`submitted` → `ready`） |
| owner | **每日報表** | 查看當日總金額與 Top 5 品項 |
| admin | **使用者管理** | 查看使用者列表並直接指派角色 |

### 訂單狀態流轉（MVP）

```
pending → submitted → ready → called
  顧客      顧客       廚師    店員
建立訂單  提交訂單  標記備餐完成  叫號取餐
```

> 評分可在 `submitted` 之後的任意狀態進行。

## 三層架構實作說明

本專案採用 V10「事實發現與依賴邏輯」架構哲學，並新增 Guards 層集中管理權限邏輯：

```
第1層 shared/contracts.ts  → 定義「這個概念是什麼」（業務真理）
         ↓
shared/guards.ts           → 定義「誰可以做這件事」（V10 新增，集中權限）
         ↓
第2層 backend.ts (routes)  → 定義「API 如何接收與回應」
         ↓
第3層 db/schema.ts         → 定義「怎麼存進資料庫」
```

下面以五項新功能為例說明。

---

### 功能一：顧客評分（customer — POST /api/orders/:id/rating）

**第1層：定義「評分」這個業務概念**

```typescript
// shared/contracts.ts
export const ratingSchema = z.object({
  orderId: z.number(),
  stars: z.number().int().min(1).max(5),
  comment: z.string().optional(),
  createdAt: z.string(),
});
```

**Guards：只有 customer 能評分、且只能評自己的訂單**

```typescript
// shared/guards.ts
requireRole(user, "customer");
await requireResourceOwner(orderId, user.id); // 確認訂單屬於自己
```

**第2層：API 路由**

```typescript
app.post("/api/orders/:id/rating", async ({ params, body, request }) => {
  const user = await requireUser(request);
  requireRole(user, "customer");
  await requireResourceOwner(params.id, user.id);
  // ...儲存評分
}, {
  body: z.object({
    stars: z.number().int().min(1).max(5),
    comment: z.string().optional(),
  }),
});
```

**第3層：ratings 資料表**

```typescript
// db/schema.ts
export const ratingsTable = appSchema.table("ratings", {
  id: integer("id").primaryKey().generatedByDefaultAsIdentity(),
  orderId: integer("order_id").notNull().unique()
    .references(() => ordersTable.id),
  userId: text("user_id").notNull().references(() => user.id),
  stars: integer("stars").notNull(),
  comment: text("comment"),
  createdAt: timestamp("created_at").defaultNow(),
});
```

### 功能四：店長每日報表（owner — GET /api/reports/daily）

**第1層：定義「每日報表」這個業務概念**

```typescript
// shared/contracts.ts
export const dailyReportSchema = z.object({
  date: z.string(),
  totalOrders: z.number(),
  totalRevenue: z.number(),
  topItems: z.array(z.object({
    itemName: z.string(),
    totalQty: z.number(),
    totalRevenue: z.number(),
  })),
});
```

**Guards**

```typescript
requireAnyRole(user, ["owner", "admin"]);
```

**第2層：API 路由**

```typescript
app.get("/api/reports/daily", async ({ query, request }) => {
  const user = await requireUser(request);
  requireAnyRole(user, ["owner", "admin"]);
  const date = query.date ?? today();
  // 聚合查詢...
}, {
  query: z.object({ date: z.string().optional() }),
});
```

**第3層：聚合查詢，不需新增資料表**

```typescript
const result = await db
  .select({
    itemName: orderItemsTable.name,
    totalQty: sql<number>`sum(${orderItemsTable.qty})`,
    totalRevenue: sql<number>`sum(${orderItemsTable.price} * ${orderItemsTable.qty})`,
  })
  .from(orderItemsTable)
  .innerJoin(ordersTable, eq(orderItemsTable.orderId, ordersTable.id))
  .where(between(ordersTable.submittedAt, startOfDay, endOfDay))
  .groupBy(orderItemsTable.name)
  .orderBy(desc(sql`sum(${orderItemsTable.qty})`))
  .limit(5);
```

### 功能五：管理員使用者管理（admin — GET /api/users、PATCH /api/admin/users/:id/roles）

**第1層：定義「帶有角色的使用者」**

```typescript
// shared/contracts.ts
export const userWithRolesSchema = z.object({
  id: z.string(),
  name: z.string(),
  email: z.string(),
  roles: z.array(roleSchema), // ← 複數陣列，與 V10 規格一致
  createdAt: z.string(),
});
```

**Guards + 業務規則**

```typescript
requireRole(user, "admin");
if (params.id === user.id) throw new Error("不能修改自己的角色");
```

**第2層：API 路由**

```typescript
// 查看使用者列表
app.get("/api/users", async ({ request }) => {
  const user = await requireUser(request);
  requireRole(user, "admin");
  // 回傳使用者列表...
});

// 直接指派角色（admin only）
app.patch("/api/admin/users/:userId/roles", async ({ params, body, request }) => {
  const user = await requireUser(request);
  requireRole(user, "admin");
  if (params.userId === user.id) throw new Error("不能修改自己的角色");
  // 更新角色...
}, {
  body: z.object({ roles: z.array(roleSchema) }),
});
```

**第3層：角色存為 user 表的 array 欄位（V10 規格）**

```typescript
// db/auth-schema.ts — 在現有 user 表新增一個欄位
export const user = appSchema.table("user", {
  // ...現有欄位不變...
  roles: text("roles").array().notNull().default(["customer"]),
  // ↑ V10_RBAC 指定使用 PostgreSQL array，效能好、查詢簡單
});
```

> **不使用獨立 user_roles 資料表**，遵循 V10_RBAC 的設計決策。

## 專案概述

本專案為早餐店前後端管理系統，以 V10 為基礎導入 RBAC（Role-Based Access Control）權限管理。系統支援五種角色，每種角色各有對應的操作範圍，確保資料安全與職責分離。

---

## 角色定義

| 角色 | 說明 |
|------|------|
| **顧客（Customer）** | 一般消費者，可自行點餐 |
| **店員（Staff）** | 負責現場服務與叫號取餐 |
| **廚師（Chef）** | 負責備餐，需看到待處理訂單 |
| **店長（Manager）** | 管理菜單與查看營運數據 |
| **系統管理員（Admin）** | 完整系統控制，管理帳號 |

---

## 功能規劃（完整願景）

### 顧客（Customer）

**基本功能**
- 瀏覽當前菜單（含分類篩選）
- 建立購物車訂單、修改數量
- 提交訂單並查看自己的訂單歷史

**進階規劃**
- 對已完成訂單給予 1–5 星評分，並可附留言
- 查看訂單目前的備餐狀態（待備餐 / 備餐中 / 可取餐）
- 收藏常點品項，下次快速重點
- 訂單完成後推播通知（取餐提醒）

---

### 店員（Staff）

**基本功能**
- 查看所有已提交的訂單
- 協助顧客完成點餐操作（代客點餐）

**進階規劃**
- 叫號管理：依時間順序將訂單標記為「已叫號」
- 查看當前等候隊列，掌握現場狀況
- 處理顧客臨時加點或修改（訂單提交前）
- 標記訂單為「已取餐」，完結整個流程

---

### 廚師（Chef）

**基本功能**
- 查看所有狀態為「已提交」的待處理訂單
- 依下單時間排序，確保先進先出

**進階規劃**
- 將完成備餐的訂單標記為「可取餐」（通知店員叫號）
- 查看各品項的今日備餐數量（備料參考）
- 標記某品項「暫時售完」，即時下架（需 manager 確認）
- 顯示備餐時間統計（平均完成速度自我監控）

---

### 店長（Manager）

**基本功能**
- 新增、修改、刪除菜單項目
- 查看所有訂單（含顧客資訊）

**進階規劃**
- 每日營業報表：總訂單數、總營業額、各品項銷售排行 Top 5
- 查看週/月趨勢圖（銷售走勢）
- 設定品項的促銷價格與有效期間
- 管理菜單分類（新增/排序分類）
- 匯出訂單報表為 CSV

---

### 系統管理員（Admin）

**基本功能**
- 擁有所有角色的完整操作權限

**進階規劃**
- 查看所有已註冊使用者列表
- 修改任意使用者的角色（不可降級自己）
- 停用帳號（軟刪除，保留訂單歷史）
- 查看系統操作紀錄（誰在何時做了什麼）
- 管理系統設定（營業時間、最大訂單數等）

## MVP 範圍

考量開發時間，本次實作以下最小可行範圍：

### 各角色核心功能（各一項新功能）

| 角色 | MVP 新功能 | 說明 |
|------|-----------|------|
| 顧客 | **訂單評分** | 對已提交訂單評 1–5 星 |
| 店員 | **叫號** | 將訂單標記為已叫號（`submitted` → `called`） |
| 廚師 | **標記出餐** | 將訂單標記為可取餐（`submitted` → `ready`） |
| 店長 | **每日報表** | 查看當日總金額與 Top 5 品項 |
| 管理員 | **使用者管理** | 查看使用者列表並修改角色 |

### 訂單狀態流轉（MVP）

```
pending → submitted → ready → called → completed
  顧客      顧客       廚師    店員
建立訂單  提交訂單   標記完成   叫號
```

## 三層架構實作說明

本專案採用「事實發現與依賴邏輯」架構哲學，每一項新功能都遵循相同的三層依賴順序設計：

```
第1層 shared/contracts.ts   → 定義「這個概念是什麼」
         ↓
第2層 shared/route-schemas.ts → 定義「誰可以做這件事、要傳什麼」
         ↓
第3層 db/schema.ts           → 定義「怎麼存進資料庫」
```

下面以五項新功能為例，說明每一層的職責。

---

### 功能一：顧客評分（Customer — POST /api/orders/:id/rating）

**第1層：定義「評分」這個業務概念**

評分是顧客與訂單之間的客觀事實，不管用什麼資料庫都存在「一筆訂單對應一個星等」這件事。

```typescript
// shared/contracts.ts
export const ratingSchema = z.object({
  orderId: z.number(),
  stars: z.number().int().min(1).max(5),
  comment: z.string().optional(),
  createdAt: z.string(),
});
```

**第2層：定義「誰可以評分、送什麼資料」**

只有 customer 能呼叫，且必須是自己的訂單。授權規則在這層明確寫出，不藏進 middleware。

```typescript
// backend.ts（route-schemas 層的體現）
app.post("/api/orders/:id/rating", async ({ params, body, request }) => {
  const user = await requireUser(request);
  requireRole(user, "customer");               // ← 授權：只有顧客
  await requireOrderOwner(params.id, user.id); // ← 授權：只能評自己的訂單
  // ...業務邏輯
}, {
  body: z.object({
    stars: z.number().int().min(1).max(5),
    comment: z.string().optional(),
  }),
  response: { 201: ratingResponseSchema, 403: apiErrorResponseSchema },
});
```

**第3層：定義「評分怎麼存進資料庫」**

`orderId` 設為 UNIQUE 約束，資料庫層保證一筆訂單只能有一筆評分。

```typescript
// db/schema.ts
export const ratingsTable = appSchema.table("ratings", {
  id: integer("id").primaryKey().generatedByDefaultAsIdentity(),
  orderId: integer("order_id").notNull().unique()
    .references(() => ordersTable.id),
  userId: text("user_id").notNull().references(() => user.id),
  stars: integer("stars").notNull(),
  comment: text("comment"),
  createdAt: timestamp("created_at").defaultNow(),
});
```

### 功能二：店員叫號（Staff — PATCH /api/orders/:id/call）

**第1層：擴充訂單狀態的業務概念**

「已叫號」是訂單生命週期裡客觀存在的一個狀態，因此加進 contracts 的狀態枚舉中。

```typescript
// shared/contracts.ts
export const orderStatusSchema = z.enum([
  "pending", "submitted", "ready", "called", "completed"
]);
```

**第2層：定義「只有店員可以叫號、只能從 ready 變 called」**

```typescript
app.patch("/api/orders/:id/call", async ({ params, request }) => {
  const user = await requireUser(request);
  requireAnyRole(user, ["staff", "admin"]);    // ← 授權

  const order = await getOrder(params.id);
  if (order.status !== "ready") {              // ← 業務規則：狀態必須正確
    throw new Error("只有備餐完成的訂單才能叫號");
  }
  // 更新狀態...
});
```

**第3層：只需更新 orders 表的 status 欄位，不需新增資料表**

```typescript
await db
  .update(ordersTable)
  .set({ status: "called", calledAt: new Date() })
  .where(eq(ordersTable.id, orderId));
```

### 功能三：廚師標記出餐（Chef — PATCH /api/orders/:id/ready）

**第1層**：同樣使用 `orderStatusSchema`，`ready` 狀態代表「廚師已完成備餐」。

**第2層：只有廚師可以將 submitted → ready**

```typescript
app.patch("/api/orders/:id/ready", async ({ params, request }) => {
  const user = await requireUser(request);
  requireAnyRole(user, ["chef", "admin"]);     // ← 授權

  const order = await getOrder(params.id);
  if (order.status !== "submitted") {
    throw new Error("只有已提交的訂單才能標記出餐");
  }
  // 更新狀態...
});
```

**第3層**：更新 `orders.status`，不需新增資料表，複用現有欄位即可。

### 功能四：店長每日報表（Manager — GET /api/reports/daily）

**第1層：定義「每日報表」這個業務概念**

報表是對訂單與品項資料的彙整，屬於可衍生出來的業務事實。

```typescript
// shared/contracts.ts
export const dailyReportSchema = z.object({
  date: z.string(),
  totalOrders: z.number(),
  totalRevenue: z.number(),
  topItems: z.array(z.object({
    itemName: z.string(),
    totalQty: z.number(),
    totalRevenue: z.number(),
  })),
});
```

**第2層：只有 manager / admin 可查，可傳日期參數**

```typescript
app.get("/api/reports/daily", async ({ query, request }) => {
  const user = await requireUser(request);
  requireAnyRole(user, ["manager", "admin"]);  // ← 授權
  const date = query.date ?? today();
  // ...
}, {
  query: z.object({ date: z.string().optional() }),
  response: { 200: dailyReportResponseSchema },
});
```

**第3層：用聚合查詢從現有的 orders、order_items 兩張表計算，不新增資料表**

```typescript
// db/schema.ts 不需異動，直接在 backend 做聚合查詢
const result = await db
  .select({
    itemName: orderItemsTable.name,
    totalQty: sql<number>`sum(${orderItemsTable.qty})`,
    totalRevenue: sql<number>`sum(${orderItemsTable.price} * ${orderItemsTable.qty})`,
  })
  .from(orderItemsTable)
  .innerJoin(ordersTable, eq(orderItemsTable.orderId, ordersTable.id))
  .where(between(ordersTable.submittedAt, startOfDay, endOfDay))
  .groupBy(orderItemsTable.name)
  .orderBy(desc(sql`sum(${orderItemsTable.qty})`))
  .limit(5);
```

**第1層：定義「帶有角色的使用者」這個業務概念**

```typescript
// shared/contracts.ts
export const userWithRoleSchema = z.object({

  email: z.string(),

  createdAt: z.string(),
```

```typescript
app.patch("/api/users/:id/role", async ({ params, body, request }) => {
  const user = await requireUser(request);
  requireRole(user, "admin");                  // ← 授權：只有 admin

  if (params.id === user.id) {
    throw new Error("不能修改自己的角色");     // ← 業務規則
  }
  // 更新角色...
}, {
  body: z.object({ role: roleSchema }),
});
```

**第3層：角色欄位存在 Better Auth 管理的 user 表，只需新增 role 欄位**

```typescript

export const userRolesTable = appSchema.table("user_roles", {
  userId: text("user_id").primaryKey().references(() => user.id),
  role: text("role").notNull().default("customer"),
```
